# Before format version 1

> **Not normative.** This is a working list for the maintainers. The rules are in [format.md](format.md). Section 13 of that file lists the open *format* items. This page adds the things that are not in the format text: security checks, decisions that we parked on purpose, and cleanups.

The format is a draft (format version 0) and changes freely. **From format version 1 on, NilPerit must read every older version forever** (ADR 0011), accepted ADRs are no longer rewritten, and strings like context strings and magic bytes become permanent. Everything below is cheap to fix now and expensive to fix later.

Remove an item when it is done. The history is in git.

## Security and audits

- **KEM implementation.** The format uses X-Wing draft 06 (`x-wing-draft-06`), through the `x-wing` crate (pure Rust). Its README says that it has never been independently audited. The `ml-kem` crate under it says the same (versions checked on 2026-11-22: `x-wing` 0.1.1, `ml-kem` 0.3.4). Before version 1:
  - check the current audit status of both crates;
  - decide whether to keep them or to switch to `libcrux-ml-kem` (formally verified, but then we have to write the X-Wing combiner ourselves);
  - check whether X-Wing is a final standard by then. If it is, give it a new algorithm name and update ADR 0012 and ADR 0018.
- **Review the seal construction** (section 3.3.2.2, ADR 0018). It is a simple KEM-DEM that we composed from reviewed parts, but nobody with cryptography expertise has reviewed the composition yet. This also covers the use of the header hash as associated data, and the context strings.
- **Audit status of the crates that handle keys or untrusted data** (as the crates' own READMEs say, checked on 2026-11-22). Re-check before version 1, and read which version an audit covered:
  - `chacha20poly1305` 0.11, `chacha20` 0.10 and `poly1305` 0.9: one NCC Group audit (2020), no significant findings. The `poly1305` README says that the audit predates its AVX2 backend, which has not been audited.
  - `x-wing` 0.1.1 and `ml-kem` 0.3.4: never independently audited.
  - `x25519-dalek` 3.0.0, `curve25519-dalek` 5.0.0, `bip39` 3.0.0 and `bitcoin_hashes` 0.14: the READMEs say nothing about audits. ADR 0012 mentions a Quarkslab audit of an older `curve25519-dalek`. We have not checked it. `bip39` only maps the root seed to words and back, but it handles the root seed.
  - `blake3`, `zeroize` and `minicbor` were added earlier. `miniz_oxide` 0.9.1 was added with the pack reader: it forbids `unsafe` code and has no independent audit that we know of. `clap` (with `clap_derive`, which brings a second major version of `syn` for the build), `getrandom` (with `libc` and `cfg-if`) and `rand_core` came with the command-line program. They are widely used, and we know of no independent audit. `getrandom` gives all the randomness for keys and nonces, so it is the one that matters most. `rpassword` 7 (with `rtoolbox`) came with `ls`: it reads the recovery phrase from the terminal without showing it, so it is in the path of the phrase. It is small, and we know of no independent audit. Still to record when they are added: `fastcdc` if a content-defined chunker comes.
- **Fuzzing.** Add fuzz targets for the strict CBOR checker, the pack parser, and the decompress-and-verify path (ADR 0016 promises the last one).
- **Review every draft constant before it freezes.** The context strings (dated `2026-11-22`), the magic bytes and end magic of a pack, and the algorithm names. Section 3.2.7 of the format says that the context strings are fixed for a format version.

## Parked format decisions

- **Describe sources in the vault.** For the first working system a source (name, connector type, selection, priority) lives only in the node's local configuration. Before version 1 the vault needs it too, so that a person can move to a new host and a reader can show names. The likely design is a small R-class *source record* object that delta entries reference, so a rename or a priority change is versioned. The record holds the description only, never connection secrets such as OAuth tokens (ADR 0004). The node writes it sealed to the read public key and cannot read it back. After a move, the owner restores the description and authorizes the sources again.
- **Rollback of the vault config.** An attacker who can replace both copies with an older valid pair cannot be detected from the files alone (section 7.2.6). A node could remember the highest config sequence that it has seen. Decide whether it should.
- **Split the recovery binary before version 1.** For now `recovery/` ships the full `nilperit` binary, so that we do not manage two binaries without a gain. Before version 1, `recovery/` MUST ship a reader-only binary (`nilperit-recover`, ADR 0014): list, restore and verify, which depend on the reader side only. The plan: the read commands are a library in the `nilperit-recover` crate, and the full binary depends on it. The restore path handles the recovery phrase, so it must stay small enough to audit. It will contain `clap` (6 crates with the reduced features) and `rpassword`. Look at them again when the lean binary is made. Fill in section 7.3 of the format then.
- **A real seal in the test vector.** The pack vector A.8 has a placeholder seal and KEM name. Replace them when the seal code exists and there is an X-Wing implementation to check against. Add the seal itself as a vector.
- **Reader: head and forks.** The reader chooses the journal head from the snapshot headers only. The selection without any snapshot header (section 5.5.10) is not built, and neither is the report of a fork (section 5.5.11): the reader follows the single chain from the newest header. Build both before a release that promises recovery from damaged snapshot headers. The same scan can serve salvage (section 10.7).
- **Strength of the writer lock.** The lock is a file with a heartbeat (section 8.6). It stops two runs by mistake, and the format says that it is not a strong lock (8.6.5): a holder that pauses for longer than the limit, clocks that differ by more than the limit, and two nodes that take over the same stale lock at once can all give two writers. We accept this for a personal vault. The second defense is fork detection (5.5.11), which is not built yet (see "Reader: head and forks" above). A target that can do an atomic compare-and-swap, or that has real locks, could give a stronger lock later.
- **Protect the credential file with an SSH key.** The node credential file is local and plain (mode 0600). A later version can wrap it for an SSH public key with the `age` format, without a change to the vault format. This only helps when a person unlocks the key: `ssh-agent` cannot do the decryption, and an unattended script needs an unlocked key file, which is as exposed as the plain file. Deriving a key from an agent signature needs a deterministic algorithm (Ed25519 or RSA, not ECDSA), lets any process that reaches the agent derive the key, and is a new construction that needs review.
- **What the folder connector leaves out.** It stores regular files with their path, their times and the permission bits (as `{"mode": 420}`). It does not store empty folders, sockets, pipes and devices (it reports them as items that cannot be read), the owner and group, extended attributes and access control lists, or a media type. A symbolic link is not stored as a link: by default it is reported and skipped, and with the option `Symlinks::Follow` the item is what the link points to, under the path of the link. A restore of a vault is therefore not a copy of the folder in every detail. Decide which of these to keep before version 1. Storing a symbolic link as a link needs a convention for the metadata and a safe restore, because a link that is restored and then written through can lead out of the destination.
- **Content-defined chunking.** The first system cuts content into chunks of one size (`fixed`, section 5.2.4). A content-defined algorithm (such as FastCDC) is deferred until a connector shows that it saves space. The cases that could gain are bytes that move: an attachment at different offsets in different emails, or a tag at the top of a media file. Measure with the Gmail connector before adding one. When we add one:
  - the format needs the exact text of the algorithm and a test vector with its cut points, so that a later upgrade of a crate cannot change the chunking silently;
  - its gear table must come from a secret, so that someone who sees range reads cannot test for known files from the chunk sizes. The proposal: add a key that derives from the root seed (a new context string, like the other keys), derive 2048 bytes from it with BLAKE3 `derive_key` and read them as 256 little-endian 64-bit numbers, and give them to `cut_gear` of the `fastcdc` crate (5.0.0: MIT, pure Rust, no `unsafe` code, checked). The seeding of that crate only XORs one 64-bit number into a public table;
- **Still open in `format.md` section 13:** the fields of a checkpoint, the type IDs and field numbers of the remaining object types, the schema dictionary generator, and the parity data format.
- **Object types still to specify:** the checkpoint, the tree nodes, the condemnation record, and the index segment (`format.md` section 13). The item record, delta entry and snapshot header are specified (ADR 0019).
- **Statistics in the snapshot header.** Only the item count and the total size for now (ADR 0019). Data that changes over time, such as which replicas hold which objects, does not fit an immutable header. Put it in an index segment or in scrub results.
- **Time precision.** Times are in milliseconds (ADR 0019). A connector that needs finer file times keeps them in its metadata. Check this when the folder connector exists.
- **Very large files.** A content object lists every chunk. With the default profile, a 1 TiB file has a content object of about 143 MB. The large profile keeps this small (about 18 MB), and profiles are chosen by the data. If TB-scale files with small chunks turn out to be common, make content objects a tree in a later schema version.
- **More compression algorithms.** zstd and LZ4 as opt-in algorithms, after we have audited a decoder. A source can already use `none`.
- **The pack trailer is a single point of failure for its pack.** We accept this (ADR 0017). Revisit it only if experience shows a problem. Replicas and parity cover it.

## Cleanups

- Section 11.3.1 of the format mentions a "combined delta entry" that the glossary does not define.
- ADR 0007 says that an item record "lives" in the same pack as its content. Section 6.2 of the format says SHOULD.

## Before the first release (not about the format)

- Run `cargo deny` on a schedule, as its own small workflow. New advisories appear without any code change, and Dependabot only opens pull requests for updates. We postponed this until we get near a release.
